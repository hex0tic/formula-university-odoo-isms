## 2. Логик алдаа ба өгөгдлийн зөрчил

### 2.1 RSK-14 — CISO-гийн батлалтгүй «Хүлээн зөвшөөрсөн» эрсдэл
- **Байсан:** `treatment = accept`, `state = residual`, `accepted_by_id` хоосон.
- **Яагаад асуудал:** Clause 6.1.3 f) — эрсдэл хүлээн зөвшөөрөх шийдвэрийг эрх бүхий этгээд гаргаж бүртгэнэ. Манай workflow үүнийг CISO-оос шаарддаг ч импорт төлөвийг шууд бичсэн тул дүрмийг тойрсон. Аудитор «хэн зөвшөөрсөн бэ?» гэж асуухад хариулт байхгүй — нотолгооны цоорхой.
- **Хийсэн:** `isms.risk._isms_repair_workflow_consistency()` — эрсдэл хариуцагч нь CISO бол батлалтыг бүртгэж chatter-т «Workflow-ийн нийцлийн засвар» гэж ил тэмдэглэнэ, эс бөгөөс анхааруулга буцаана. Migration-ээр ажиллуулсан; `import_case_data.py` цаашид импорт бүрийн төгсгөлд өөрөө ажиллуулна.
- **Баталгаа:** DB-д RSK-14 `accepted_by = dorjsembe (CISO)`; chatter тэмдэглэлтэй.

### 2.2 INC-2026-0001 — хувийн мэдээллийн зөрчил мэдэгдлийн шийдвэргүй хаагдсан

## 3. Эрхийн хяналт (RBAC) ба нууцлалын алдаа

### 3.1 Мэдээлэгч (оюутан, багш) хязгаарлагдмал бүртгэлийг уншиж чаддаг байсан
- **Байсан:** Reporter бүлэгт `isms.asset` унших ACL байсан (инцидентэд хөрөнгө сонгуулахын тулд). Үр дүнд нь RPC-ээр бүх 16 хөрөнгийн нэр, «Нууц» ангилал, байршил (серверийн өрөө), эзэмшигч, мөн SoA-ийн «Odoo дахь хэрэгжилт», «нотолгоо»-г уншиж болно. Inventory catalog/lot дээрх `related` талбарууд sudo-оор тооцогддог тул бараа унших эрхтэй **бүх** дотоод хэрэглэгч ISMS ангилал, эрсдэлийг харж байсан.
- **Яагаад асуудал:** A.5.12 (ангилал), A.5.15/A.8.3 (хандалтыг хэрэгцээгээр хязгаарлах, least privilege). Хөрөнгийн бүртгэл ба хамгаалалтын нарийвчилсан хэрэгжилт нь халдагчид «газрын зураг» болно. Цэс нуусан нь хамгаалалт биш — RPC шууд хандана.
- **Хийсэн:** Reporter-ийн хөрөнгийн ACL-ийг устгав; инцидентийн `asset_ids/risk_ids/control_ids`, SoA-ийн `justification/odoo_implementation/evidence`, product/lot дээрх ISMS талбарт `groups`; **Odoo 18 field `groups` нь create-д хамгаалдаггүйг тест илрүүлсэн** тул create/write-д холбоосын тодорхой шалгалт нэмэв. Хөрөнгийг МАБ-ын баг шалгалтын үед холбоно.
- **Баталгаа:** бодит HTTP-ээр `lecturer_cs` — хөрөнгө, SoA дэлгэрэнгүй, хөрөнгө холбох, барааны ISMS талбар, PDF бүгд AccessError/403.

### 3.2 Campus-ийн хэрэглэгчид инцидент мэдээлж чаддаггүй байсан
- **Байсан:** 7 campus хэрэглэгч (оюутан, багш, бүртгэл, reviewer, auditor) ISMS-ийн ямар ч эрхгүй. SoA 6.8-д «бүх хэрэглэгч мэдээлнэ» гэж бичсэн нь бодит байдалтай зөрж байсан.
- **Яагаад асуудал:** A.6.8 — бүх ажилтан, холбогдох тал аюулгүй байдлын үйл явдлыг тогтоосон сувгаар мэдээлэх ёстой. Кейсийн гол аюул (фишинг, хуурамч «дүн засах» хүсэлт) оюутан, багшид ирдэг тул тэд мэдээлэх боломжгүй бол илрүүлэлт хоцорно. Мөн SoA-ийн мэдэгдэл худал болох эрсдэл.
- **Хийсэн:** `campus_university.group_campus_user` ⇒ ISMS Reporter (bridge модульд). 3.1-ийн засварын дараа хийсэн тул Reporter болсон оюутан хязгаарлагдмал бүртгэл харахгүй.
- **Баталгаа:** bridge тест — бүртгэлийн ажилтан инцидент үүсгэж Report хийнэ, хөрөнгийн бүртгэл AccessError; DB-д 7/7 campus хэрэглэгч Reporter.

### 3.3 `admin` техникийн данс CISO эрхтэй байсан
- **Байсан:** миний анхны security XML-ээр `admin` нь «МАБ менежер (CISO)» (+ шинжээч, эзэмшигч, аудитор).
- **Яагаад асуудал:** A.5.3 үүрэг салгах, A.8.2 давуу эрх. Системийн админ эрсдэл хүлээн зөвшөөрөх, бодлого батлах, инцидент хаах, өөрийн үйлдлийн аудит логийг хянах — нэг хүнд хэт их эрх, хуваалцсан техникийн данс бизнес шийдвэр гаргах нь хариуцлагыг бүдгэрүүлнэ.
- **Хийсэн:** XML-ээс хасаж, migration-ээр одоо байгаа DB-д `admin` = Мэдээлэгч + Settings болгов (эрхийн өөрчлөлт аудит логт бичигдсэн). Мониторингийн CISO жагсаалтаас admin-ийг хасав.
- **Баталгаа:** test_24; DB-д admin-ийн ISMS бүлэг зөвхөн «1. Мэдээлэгч».

### 3.4 Дотоод аудитор PDF тайлан хэвлэж чаддаггүй байсан
- **Байсан:** «Тайлан» цэсний server action-ууд Odoo 18-д `groups_id`-гүй бол моделийн **write** эрх шаарддаг. Аудитор зөвхөн уншдаг тул SoA/эрсдэл/хөрөнгийн PDF хэвлэх нь AccessError өгдөг байсан (шинжээчээр шалгагдсан тул анзаарагдаагүй).
- **Яагаад асуудал:** A.5.35 хараат бус хяналт — аудитор SoA, эрсдэлийн бүртгэлийг өөрөө гаргаж шалгах ёстой; эс бөгөөс өөрчлөх эрхтэй хүнээс хамаарна.
- **Хийсэн:** бүх тайлангийн action-д `groups_id` (шинжээч, аудитор), мониторингийнхэд CISO. Аудиторт хөрөнгө унших ACL-ийг тусад нь өгөв (3.1-ийн засвар үүнийг санамсаргүй хассан байсныг тест илрүүлсэн).
- **Баталгаа:** test_25; бодит HTTP-ээр `telmuun` (аудитор) SoA, удирдлагын PDF хэвлэнэ, мониторинг хориотой.

### 3.5 Дотоод workflow token дуудагч руу «урсах»
- **Байсан:** систем дотроос үүсгэсэн бичлэг (жишээ: автомат инцидент) дотоод token-той context-оо авч буцдаг байсан; дараа нь тэр бичлэгээр хэрэглэгч `with_user()` хийвэл хамгаалалтыг тойрох боломжтой (test_22 илрүүлэв).
- **Яагаад асуудал:** RPC-ээр шууд ашиглагдахгүй ч ирээдүйн код ийм бичлэгийг хэрэглэгчид дамжуулбал хамгаалалт чимээгүй унтарна — аюулгүй бус default.
- **Хийсэн:** буцаахдаа цэвэр context-той `browse` хийнэ.

## 4. Орчин ба ажиллагааны алдаа

### 4.1 Regression тест ашиглалтын DB дээр ажилладаг байсан
- **Байсан:** `odoo-cli.sh -u ... --test-enable` нь `orgil_isms` дээр тест ажиллуулдаг. Тест rollback хийдэг ч PostgreSQL sequence буцдаггүй тул инцидентийн дугаар INC-2026-0021 → **0070** болж үсэрсэн; тестийн хэрэглэгч, бичлэг ашиглалтын өгөгдөлтэй нэг DB-д үүсдэг.
- **Яагаад асуудал:** A.8.31 хөгжүүлэлт/тест/ашиглалтын орчныг тусгаарлах, A.8.33 тестийн мэдээлэл. Дугаарлалтын цоорхой нь аудиторт «бичлэг устгагдсан уу?» гэсэн сэжиг төрүүлнэ; тест алдаатай бол ашиглалтын өгөгдөл эвдэрч болно.
- **Хийсэн:** `scripts/run-tests.sh` — шинэ `isms_ci_<огноо>` DB үүсгэж модулиудыг demo-гүй суулгаад тестлэж, DB ба filestore-ийг устгана. Энэ нь шинэ орчинд бүрэн суулгах замыг ч давхар баталдаг. `operations.md`, `odoo-guide.md` шинэчлэв.

### 4.2 PostgreSQL backend segfault
- **Байсан:** тестийн нэг run-д `server process terminated by signal 11`; Postgres бүх холболтыг тасалж recovery хийсэн. Ашиглалтын DB бүрэн бүтэн (шалгасан), түр DB-г гараар цэвэрлэв, дахин run PASS.
- **Яагаад асуудал:** A.8.14/хүртээмж — DB-ийн процессын унталт ашиглалтын үед хүсэлт тасална. Alpine/musl дээрх LLVM JIT нь ийм унталтын мэдэгдэж буй шалтгаан, Odoo-гийн OLTP ачаалалд JIT ашиггүй.
- **Хийсэн:** `ALTER SYSTEM SET jit = off` (restart-гүй), `docker-compose.yml`-д `-c jit=off`. Үйл явдлыг worklog-д бүртгэв.
